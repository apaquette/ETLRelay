    etlrelay.core.source.Source ¶

    Bases: Protocol

    Define the interface for components that produce data batches.

    Concrete source implementations are responsible for obtaining data from their respective data sources and exposing it as an iterable of Batch objects.

    The protocol is runtime-checkable, allowing implementations to be checked for protocol conformance using isinstance().

    etlrelay.core.processor.Processor ¶

    Bases: Protocol

    Define the interface for ETLRelay batch processors.

    A processor accepts a Batch, applies a transformation, and returns the resulting Batch. Processors are executed sequentially by the pipeline.

    The protocol allows different processor implementations to be used interchangeably without coupling the pipeline to concrete classes.

    Pipeline¶

    etlrelay.pipeline.pipeline.Pipeline ¶

    Coordinate batch processing between a source, processors, and a sink.

    The pipeline obtains batches from a source, applies each configured processor in sequence, and passes the resulting batches to the sink.

    An empty processor sequence allows batches to pass through unchanged. Processing is synchronous, and exceptions from the source, processors, or sink propagate to the caller.

    __init__(source, processors, sink) ¶

    Initialize the pipeline with its source, processors, and sink.

    Parameters:

    Name Type Description Default
    source Source

    Component that produces batches for processing.

    		 required
    processors Sequence[Processor]

    Ordered sequence of processors to apply to each batch. May be empty if no transformations are required.

    		 required
    sink Sink

    Component that consumes the processed batches.

    		 required

    run() ¶

    Execute the pipeline and deliver processed batches to the sink.

    Batches are obtained from the source, processed in sequence, and passed to the sink as an iterable. Processing is lazy, avoiding buffering all batches in memory before writing.

    Raises:

    Type Description
    Exception

    Exceptions raised during source iteration, processing, or sink execution propagate to the caller.

    Filesystem and security¶

    etlrelay.security.path.PathValidator ¶

    Validate filesystem paths against a trusted base directory.

    PathValidator resolves both the configured base directory and candidate paths before checking whether the candidate remains within the permitted directory. This prevents path traversal and symlink-based paths from escaping the configured boundary.

    Parameters:

    Name Type Description Default
    base_path Path | None

    The directory that candidate paths must remain within. If None, the current working directory is used.

    		 None

    Raises:

    Type Description
    PathValidationError

    Raised by validate() when a candidate path is outside the base directory or does not exist.

    validate(path) ¶

    Validate and resolve a filesystem path.

    The candidate path is resolved relative to the configured base directory. The resolved path must remain within the base directory and must exist on the filesystem.

    Parameters:

    Name Type Description Default
    path Path | str

    The filesystem path to validate. May be a Path object or a string. Relative paths are resolved relative to the configured base directory.

    		 required

    Returns:

    Type Description
    Path

    The resolved Path for the validated filesystem location.

    Raises:

    Type Description
    PathValidationError

    If the resolved path is outside the configured base directory or does not exist.
