    v0.9.0 Beta Readiness and Feedback¶

    Ticket: 0.9.0-08, #139. Review date and target release date: 2026-10-21. Integrated baseline: 1b0993b1b5bc012754c5c3960c6b79f21d36f189.

    Release completion¶

    v0.9.0 was published on 2026-10-21. The completed release verification record contains final CI, TestPyPI, PyPI, GitHub release, and documentation evidence. Tickets #139 and #37 are closed. The preparation review below remains historical evidence; its then-pending publication gates have been completed.

    External beta feedback is optional, and none is claimed to have been collected. Maintainer verification establishes v1.0.0 readiness without a mandatory waiting period or RC cycle. See the stable-release record and compatibility policy. Future enhancements belong to a separate post-v1.0 roadmap review.

    Decision¶

    The intended v1.0 feature set is implemented and frozen. Preceding tickets 0.9.0-01 through 0.9.0-07 are closed, their reviews and tests are integrated, and no unresolved product release blocker was found in the public issue review. The source is prepared as v0.9.0 — feature-complete beta, using the existing release process. Release-facing documentation describes v0.9.0; it is not a claim that publication jobs have already run.

    The reviewed product is synchronous local CSV/Parquet and SQLite-backed SQL pipelines, the existing select/rename/filter processors, direct Python composition, YAML schema version 1, and CLI execution. Mapping-shaped documents use KeyValueReader; tabular protocols use TabularReader and TabularWriter. No required runtime feature remains incomplete. A beta milestone does not make the pre-1.0 public API a stable v1.0 compatibility promise.

    Issue review and remaining work¶

    The public open-issue list was reviewed on 2026-10-21. It contained only the parent milestone #37 and this final review ticket #139; neither reported a separate unresolved defect. All seven prerequisite tickets were confirmed closed. This is a dated review, not a guarantee against newly reported defects; repeat the check before merge.

    Classification Remaining work and disposition
    Required release gate Pass CI for the integrated v0.9.0 commit, record its SHA/run, review any newly opened defects, and complete RELEASE_CHECKS.md. Do not promote a failing candidate.
    Required publication work Run the existing TestPyPI rehearsal, promote reviewed dev to main, verify PyPI, generated v0.9.0 tag/GitHub release and hosted 0.9.0 documentation. These actions have not been performed by this source review.
    Required fix if discovered Incorrect data/schema results, resource leaks, credential exposure in controlled diagnostics, supported-environment installation failures, or documented API/CLI regressions block release until fixed and regression-tested.
    Known limitation Non-atomic/truncating file writes and partial or unreadable output after failure; SQL append-only output to existing tables and per-batch commits; SQL result materialization; path containment is not a sandbox; no universal third-party exception/log redaction. These remain explicit in security and API references.
    Later release work S3/HDFS, additional formats/processors/databases, dynamic plugins, scheduling/retries/distributed execution, SQL creation/upsert/pipeline-wide transactions, mapping-document writing, and generic row-record conversion remain outside the frozen boundary. A feature request does not become a v0.9.0 blocker.
    Later tooling maintenance Review mike/verspec dependency maintenance before future releases. The current audit reports verspec archived but no known vulnerability and exits successfully; it is documentation tooling, not a runtime dependency. No dependency-ignore rule or unsupported security claim is introduced.
    Feedback follow-up Gather the focused feedback below, correct defects within scope, then perform final v1.0 release-candidate validation. Feedback is not claimed to have been collected by this review.

    Focused beta feedback¶

    Use the v0.9.0 quick start, maintained examples, and migration guide. Check a small representative workflow:

    • Installation: Does etlrelay==0.9.0 install in a clean environment on a declared combination? Do imports, etlrelay version, and help work?
    • Usability: Can you follow the quick start, validate YAML, execute the job, and understand an invalid-configuration diagnostic and exit code?
    • API clarity: Are tabular batches versus mapping documents, constructor arguments, schema rules, stream ownership, and engine cleanup clear?
    • Correctness: Do output records, types, column order, null behavior, and processor ordering match expectations? Are empty inputs and failures consistent with documented persistence and cleanup behavior?

    Report non-sensitive defects through GitHub Issues. Include the package version, Python/OS, artifact/install method, minimal synthetic input/configuration, reproduction commands, expected versus actual output, and exit code. Include the source commit when testing an unpublished archive. Remove credentials, resolved connection URLs, production records, and sensitive logs before posting. Report suspected vulnerabilities privately following the Security Policy.

    For each report, reproduce it and classify it as a required fix, documented known limitation, or deferred enhancement. A release-blocking defect needs a focused regression test and a rerun of affected checks; published fixes require a new version rather than replacing v0.9.0 files. Track enhancements separately without expanding the beta scope. Do not mark feedback collected until actual reports or review sessions have been recorded.
